01از اینجا شروع کنید

این بسته، فرانت‌اند سایت مارپیچ صنعت است. صفحات با HTML، Tailwind و JavaScript نوشته شده‌اند و Vite فایل‌های مشترک را هنگام اجرا و build به هم متصل می‌کند. محتوای نمونه در HTML و JSON قرار دارد؛ دیتابیس و CMS هنوز به پروژه متصل نشده‌اند.

۱۱ صفحهورودی مستقل، هدر و فوتر مشترک
بدون فریم‌ورک UIES Modules و کامپوننت‌های HTML
مسیر اتصال: ASP.NET Coreانتقال قالب‌ها به Razor و تغذیه از CMS

برای شروع، پروژه را اجرا کنید، نقشه صفحات را ببینید و سپس بخش «اتصال به Razor» را بخوانید. نام فیلدها و رویدادهای این سند از سورس همین بسته استخراج شده‌اند. هرجا مدلی یا آدرسی پیشنهاد شده، صریحاً مشخص شده است.

تصاویر، فونت‌ها و فایل‌های عمومی عمداً در ZIP ارسالی قرار نگرفته‌اند. پوشه‌های اصلی باید با همان نام و مسیر به پروژه برگردند. نبودن این فایل‌ها در این بسته، به معنی حذف آن‌ها از پروژه اصلی نیست.

02اجرا و خروجی گرفتن

نسخه Node باید حداقل 22.12.0 باشد. وابستگی‌ها را از lockfile نصب کنید تا نسخه‌های بررسی‌شده حفظ شوند.

npm ci
npm run check
npm run dev

Vite آدرس محیط اجرا را در ترمینال چاپ می‌کند. بازکردن HTML با دوبار کلیک یا Live Server، includeهای پروژه را پردازش نمی‌کند؛ فایل مستند حاضر مستقل است و با دوبار کلیک باز می‌شود.

npm run check:assets
npm run build
npm run preview
فرمان / مسیرکاربرد
npm run checkساختار ۱۱ صفحه، importها، شناسه‌ها، لینک‌های داخلی و renderer امن را بررسی می‌کند.
npm run check:assetsوجود تمام مسیرهای تصویر و فونت را در public بررسی می‌کند؛ تا بازگشت assets خروجی ناموفق طبیعی است.
npm run buildHTML نهایی، فایل‌های بهینه‌شده و manifest را در dist می‌سازد.
dist/.vite/manifest.jsonنام واقعی JS/CSS خروجی و وابستگی‌های مشترک برای اتصال به Razor.
npm run previewبررسی خروجی production؛ پیش‌نمایش ورود آزمایشی در این حالت فعال نیست.

ساخت پروژه با نبودن فایل‌های public نیز ممکن است موفق شود؛ این موفقیت جای بررسی تصاویر و فونت‌ها را نمی‌گیرد. خروجی dist و node_modules در بسته تحویل قرار نگرفته‌اند و با فرمان‌های بالا تولید می‌شوند.

این پروژه SPA نیست و router مرورگر ندارد. هر لینک، یک صفحه HTML مستقل را باز می‌کند. بعد از انتقال به بک‌اند، routeهای سرور جای نام فایل‌های HTML را می‌گیرند.

05کامپوننت‌ها و قرارداد قالب

نمونه include در HTML و نحوه انتخاب داده:

<!-- @include header -->
<!-- @include search-panel search -->
<!-- @include product-cards products -->
<!-- @include catalog-consultation consultation -->

در خط دوم، search-panel نام renderer و search کلید فایل JSON همان صفحه است. {{field}} متن escape‌شده و {{{fragment}}} قطعه HTML ساخته‌شده توسط renderer داخلی است. محتوای دلخواه CMS نباید به fragment خام تبدیل شود.

قالب / rendererمصرف و نکته اتصال
header / mobile-menu / footer / auth-modalچهار partial عمومی همه صفحات؛ آرگومان JSON ندارند. منو و dialog مستقیماً زیر body بمانند.
consultationHome، About، Expertise؛ دو فرم desktop/mobile و هماهنگ‌سازی مقدار فیلدها.
catalog-consultationCTA سایر صفحه‌ها به جز Contact؛ نام فیلد دوم از secondaryName می‌آید.
search-panelProducts، Air handling، Industries؛ filters/options و id مستقل دارد.
product-cards → product-cardفهرست products در Products و Air handling؛ specs آرایه متن است.
testimonialsفقط variantهای projects و industry-textile در renderer پشتیبانی شده‌اند؛ قالب track و card مربوط به variant انتخاب می‌شود.
faq → faq-itemFAQ فعلی در Industry textile؛ id هر مورد از id بخش و شماره ساخته می‌شود. initialOpen صفرمبنا است.

فایل‌های request-form.html، testimonials.html، testimonial-card.html و product-card-air-handling.html در مسیر renderer فعلی استفاده نمی‌شوند. برای حفظ سابقه باقی مانده‌اند؛ آن‌ها را مرجع خروجی زنده در نظر نگیرید.

هنگام تبدیل به Razor، نام کلاس‌ها، ترتیب wrapperها، data-*، id و ارتباط aria-controls/aria-labelledby را حفظ کنید. لینک منوی والد در صفحات جزئیات aria-current="true" می‌گیرد؛ خود صفحه اصلی آن بخش aria-current="page".

منوی دسکتاپ از ۱۱۸۰ پیکسل فعال می‌شود؛ زیر آن منوی همبرگری است. این مقدار مستقل از breakpointهای بخش‌های دیگر است؛ مثلاً چیدمان فوتر از ۱۰۲۴ تغییر می‌کند. RTL سراسری است، اما ردیف‌های مشخصی مثل بخشی از جستجو، لوگو و محتوای فنی عمداً LTR هستند.

کلاس‌های details-card، details-table و extras-panel در دو صفحه جزئیات مشترک‌اند. خط‌های جداکننده با gradient CSS ساخته شده‌اند و فایل SVG جدا نیاز ندارند. داده ردیف‌ها را جایگزین کنید؛ نسبت ستون‌ها و wrapperها را تغییر ندهید. زیر 73.75rem بخش فنی روی هم قرار می‌گیرد.

CTA هیروی خانه و برش تصاویر Expertise از طرح فعلی پیروی می‌کنند. دکمه محصولات در هیرو پس‌زمینه شفاف و فقط stroke گرادینتی دارد. برای اصلاح یک صفحه، ابتدا CSS همان صفحه را تغییر دهید؛ override عمومی آخرین انتخاب باشد.

Tailwind باید کلاس‌های مورد استفاده Razor را در زمان build ببیند. اگر قالب‌ها به پوشه Views منتقل شدند، مسیر واقعی آن‌ها را با @source اضافه کنید. کلاس‌هایی مثل رنگ یا اندازه را با رشته‌سازی از داده CMS نسازید؛ از مجموعه محدود و صریح استفاده کنید.

07پترن هدر و فوتر

پترن یک SVG تولیدشده در مرورگر است؛ برای آن تصویری از assets درخواست نمی‌شود. هندسه مسیرها و تنظیمات از src/data/patterns/site-pattern.json می‌آید و همان خروجی نهایی Pattern Studio مبنای اجراست. رنگ، گرادینت، موج، نور متحرک و opacity در integration سایت override نمی‌شوند.

محلرفتار فعلی
هدر داخلیدر والد مستقیم .site-header نصب می‌شود و صحنه پترن با ابعاد authored خود اجرا می‌شود.
هدر خانههیروی تصویری اختصاصی دارد؛ پترن هدر مشترک عمداً نصب نمی‌شود.
فوتر همه صفحه‌هاهمان پترن و animation مرجع استفاده می‌شود؛ SVG برای پرکردن ارتفاع footer کشیده نمی‌شود و opacity/light جداگانه ندارد.
Responsiveطبق فایل مرجع، تا عرض 463px پروفایل mobile و از 464px به بالا پروفایل desktop فعال است؛ interpolation بین این دو انجام نمی‌شود.
هندسه مسیرهاstroke-width دقیقاً از تنظیم هر line خوانده می‌شود؛ minimum stroke یا non-scaling-stroke اضافی اعمال نمی‌شود.
لایه‌بندیhost با isolation:isolate؛ لایه پترن z-index:-1 و pointer-events:none دارد تا مزاحم محتوای تعاملی نباشد.
دسترس‌پذیری و مصرفaria-hidden، توقف حرکت در prefers-reduced-motion، خارج محدوده دید و تب پنهان؛ بدون درخواست شبکه.

مقادیر x/y/width/rotation/scaleY/opacity/motion/light و تنظیمات animation در JSON مرجع نگهداری می‌شوند. ارتفاع صحنه نیز همان 430px دسکتاپ و 404px موبایل خروجی ادیتور است؛ container سایت فقط آن را clip می‌کند و هندسه را تغییر نمی‌دهد.

ساختار والد هدر در Razor باید حفظ شود و بین host و لایه پترن stacking context اضافه نشود. initSitePatterns هنگام اجرای تکراری، لایه دوم نمی‌سازد.

در هر دو رویداد ثبت، event.detail شامل { form, formData } است. رویداد bubbles و cancelable است. adapter باید پیش از اولین await، preventDefault را اجرا کند تا پیام «سرویس متصل نیست» نمایش داده نشود. خود adapter مسئول loading، موفقیت، خطا و جلوگیری از ثبت تکراری است.

نمونه زیر الگوی اتصال است؛ endpoint نمونه باید با route واقعی سرور جایگزین شود. این کد به پروژه فعال اضافه نشده است.

document.addEventListener("rfq:submit", async (event) => {
    event.preventDefault(); // Claim synchronously, before awaiting.
    const { form, formData } = event.detail;
    if (form.dataset.sending === "true") return;
    const button = form.querySelector('[type="submit"]');
    const status = document.querySelector('[data-form-status]');
    const csrf = document.querySelector('meta[name="csrf-token"]')?.content;
    form.dataset.sending = "true";
    if (button) button.disabled = true;
    status.classList.remove("hidden");
    status.textContent = "در حال ارسال درخواست…";
    try {
        const response = await fetch("/api/requests/rfq", {
            method: "POST", credentials: "same-origin",
            headers: csrf ? { "X-CSRF-TOKEN": csrf } : {},
            body: formData // Do not set multipart Content-Type manually.
        });
        const result = await response.json().catch(() => null);
        if (!response.ok || result?.ok !== true) {
            throw new Error(result?.message || "ثبت درخواست انجام نشد.");
        }
        status.textContent = result.message || "درخواست ثبت شد.";
        // Reset only after server confirmation; also reset the file label.
    } catch (error) {
        status.textContent = error.message || "ارتباط برقرار نشد.";
    } finally {
        delete form.dataset.sending;
        if (button) button.disabled = false;
    }
});

فایل RFQ اختیاری است: PDF، DWG، DOC و DOCX تا ۲۰ MiB. بررسی مرورگر فقط کمک به کاربر است؛ در سرور اندازه، پسوند، محتوای واقعی و مجوز دریافت دوباره بررسی شوند. branch یکی از tehran/mashhad و requestType یکی از consultation/rfq/partnership/support است. این مقادیر فعلی‌اند و در صورت تغییر CMS باید دو سمت هماهنگ شوند.

CTAهای دارای فیلد company، تلفن یا ایمیل ندارند. پیش از فعال‌کردن ثبت واقعی، درباره افزودن راه تماس یا الزام حساب تأییدشده تصمیم بگیرید. بهتر است payloadهای متفاوت را در adapter به DTO واحد نگاشت کنید و همراه درخواست، صفحه/محصول/پروژه مرجع را بفرستید؛ شناسه مرجع نیز در سرور اعتبارسنجی شود.

11ورود، OTP و قرارداد API

در محیط dev، اگر VITE_AUTH_MODE برابر api نباشد، رابط ورود در حالت preview اجرا می‌شود. کد ۱۲۳۴۵۶ فقط برای پیش‌نمایش است و حساب یا session واقعی ایجاد نمی‌کند. در build production، preview غیرفعال است؛ تا API تنظیم نشود سرویس ورود فعال نیست.

VITE_AUTH_MODE=api
VITE_AUTH_API_BASE=/api/auth

این متغیرها در build خوانده می‌شوند و عمومی‌اند. پس از تغییرشان build تازه لازم است؛ هیچ secret در VITE_* قرار نگیرد. قرارداد فعلی از POST با JSON و credentials:same-origin استفاده می‌کند؛ مسیر API بهتر است روی همان origin باشد.

مسیر نسبیدرخواست فعلیپاسخ مورد انتظار
POST /loginidentifier, password, remember{ ok: true, user? }
POST /registerfullName, identifier, password{ ok: true, challengeId, retryAfter? }
POST /request-codeidentifier, purpose, challengeId?{ ok: true, challengeId, retryAfter? }

identifier شماره همراه یا ایمیل و purpose یکی از login/register/reset است. confirmPassword در UI بررسی می‌شود و به API ارسال نمی‌شود. retryAfter بر حسب ثانیه است. سرور برای خطا JSON دارای message و در صورت نیاز ok:false برگرداند. پاسخ ۲۰۰ بدون ok:true نیز توسط فرانت رد می‌شود. برای ۴۲۹، header عددی Retry-After خوانده می‌شود؛ خطاهای ۵xx پیام عمومی دارند.

توکن CSRF از meta با نام csrf-token به header با نام X-CSRF-TOKEN منتقل می‌شود؛ سرور باید همین نام header را بپذیرد و توکن معتبر در HTML بگذارد. session را سرور با cookie امن مدیریت کند. رمز، OTP و session token در localStorage/sessionStorage نگهداری نمی‌شوند؛ challenge و resetToken موقت در حافظه UI قرار دارند.

پس از موفقیت واقعی ورود/تأیید ثبت‌نام، auth:success روی document با { user, purpose } منتشر می‌شود. بروزرسانی هدر حساب، هدایت کاربر و پنل/خروج هنوز پیاده نشده‌اند. reset-password به فرم ورود برمی‌گردد. بررسی مجوز دانلود، rate limit، انقضای OTP، تعداد تلاش و یک‌بارمصرف‌بودن resetToken مسئولیت سرور است.

  2. partialهای مشترک را منتقل کنید؛ باقیمانده commentهای @include در Razor خودکار پردازش نمی‌شوند.
  3. داده‌های نمونه JSON و HTML را به ViewModel تبدیل کنید. Razor متن را encode کند؛ HTML خام CMS فقط پس از sanitization مجاز است.
  4. هر صفحه فقط entry خودش را بارگذاری کند. به عنوان مثال محصولات به entry مربوط به products.html متصل می‌شود، نه تمام JSهای صفحات.
  5. فرم‌ها و Auth را با قراردادهای این سند متصل کنید؛ لینک‌ها و assetها را با route نهایی تطبیق دهید.

خواندن manifest

در خروجی فعلی، کلیدهای entry نام HTML هستند؛ مثل products.html. مقدار file مسیر JS و css آرایه CSS همان chunk است. CSS مشترک ممکن است در importsهای وابسته قرار گرفته باشد. خواندن فقط cssِ entry می‌تواند استایل عمومی را حذف کند.

function collectCss(manifest, key, seen = new Set(), result = new Set()) {
    if (seen.has(key)) return result;
    seen.add(key);
    const chunk = manifest[key];
    if (!chunk) throw new Error(`Missing manifest entry: ${key}`);
    for (const imported of chunk.imports ?? []) {
        collectCss(manifest, imported, seen, result);
    }
    for (const css of chunk.css ?? []) result.add(css);
    return result;
}

نام hashدار را در Razor hardcode نکنید. ترتیب CSS مشترک و اختصاصی باید با manifest حفظ شود و مسیر تکراری دوباره درج نشود. فایل‌های static را از dist کپی کنید؛ HTML خروجی dist برای مرجع ظاهر است و جای Viewهای داینامیک نهایی را نمی‌گیرد.

URLهای /assets و /fonts ریشه‌ای هستند. اگر سایت زیر sub-path نصب شود، base مسیر Vite و URLهای قالب، فونت و فایل‌های public باید هم‌زمان سازگار شوند. تنظیم فقط base برای تمام URLهای hardcodeشده کافی نیست. در انتشار معمول روی ریشه دامنه، همین مسیرهای فعلی قابل حفظ‌اند.
